# Passkeys (WebAuthn) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let users satisfy the second factor with Face ID, fingerprint or device PIN (a passkey) instead of typing a TOTP code, keeping TOTP and backup codes as fallback.

**Architecture:** A new `services/webauthn.py` beside `services/mfa.py` owns challenges, registration and assertion verification through `py_webauthn`; state lives in two Postgres tables. Login keeps its two-step shape: the password step returns `mfa_token`, a new `passkey-verify` endpoint finishes through the same `_signed_in_response`. The frontend uses the native `navigator.credentials` API behind one service module.

**Tech Stack:** Django 6 + DRF, `webauthn` (py_webauthn, new, owner-approved), `cryptography` (pinned), React 19 + vitest, Playwright (Chromium virtual authenticator).

**Spec:** `docs/superpowers/specs/2026-11-18-passkeys-design.md`

## Global Constraints

- Passkey is an alternative second factor; TOTP, backup codes and `/django-admin/` login stay unchanged.
- RP ID in production is `tracker2.integrit.org`; dev defaults `localhost` / `http://localhost:5173`.
- Challenge lifetime 120 s, single use, stored in Postgres under `select_for_update` (never Redis).
- `UserVerificationRequirement.REQUIRED`; `attestation` is `none`; origin and RP ID pinned.
- No token is minted before a factor passes; any config or decode failure fails closed (503 or 4xx, never password-only).
- Wrong attempts share `UserMFA.failed_attempts` (5 failures, 15 min lock).
- Max 20 characters per audit action name unless the column is verified longer.
- No new npm package. Django commands run with `py -3.14`.
- No `prompt()`/`confirm()`; copy never says "TL"; keep diffs minimal (CLAUDE.md YAGNI ladder).

## Review Focus

Each line is pinned by a test in the named task.

1. Two sign-ins start at once: each gets its own challenge and one consuming does not break the other (Task 4).
2. Passkey-only user (no TOTP seed) with `mfa_required` on is still challenged, never password-only (Task 6).
3. The same authenticator registered twice returns 409, not 500 (Task 4).
4. Authenticator reports `sign_count` 0 forever or missing `transports`: accepted, no crash (Task 5).
5. Production with an `http` origin, wrong RP ID or unset variable refuses to boot (Task 1).
