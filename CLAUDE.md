## Universal Safety Rules

- Do not bypass security checks, migrations, hooks, or tests.
- Never commit or push unless explicitly requested.
- Do not scan unrelated documentation, generated files, logs, node_modules, venv, or .git.
- Load the routed context file (Task Router below) before coding and check its invariants — do not reapply fixes already documented as complete.
- Use TDD for implementation and bug fixes (write/update targeted test -> fail -> implement -> pass).

## Minimal Code & YAGNI Execution Ladder

Before writing or modifying any code, follow this mandatory 7-step ladder:

1. **YAGNI Gate:** Ask "Is this feature or abstraction explicitly requested?" If not, do not build it.
2. **Reuse First:** Search the codebase for existing utilities, UI components, serializers, or services before creating new ones.
3. **Standard Library:** Prefer native Python standard libraries or built-in JavaScript/React features over custom helper functions.
4. **Existing Dependencies:** Use packages already present in `requirements.txt` or `package.json`. Do not introduce new packages without permission.
5. **Smallest Viable Diff:** Choose the smallest clean change (e.g., single-line fix or minor function edit) over multi-file refactoring.
6. **Zero Speculative Code:** No placeholder methods, unused parameters, unneeded catch blocks, or "future-proofing."
7. **Verify & Validate:** Run targeted tests to verify the minimal change before completing the task.

## Terminal Hygiene & Output Bounding

- **Quiet Flags:** Always run terminal commands with quiet/concise flags (`pip install -q`, `npm install --silent`, `python -m ruff check --output-format=concise`).
- **Targeted Reads:** Use bounded output (`head`, `tail`, `git diff --stat`, or targeted `grep`) instead of dumping raw log files or huge terminal outputs into the context window.
- **Excluded Paths:** Exclude `node_modules/`, `venv/`, `.git/`, generated bundles, logs, and `.devin/tracking/` archives from broad searches unless explicitly requested.
- **Execution Strategy:** Run only targeted unit tests while iterating; run the full verification suite exactly once at the end of implementation.

## Hot Invariants

- **"Plugin pages won't open" is usually Vite, not Django (2026-10-04)** — `504 (Outdated Optimize Dep)` / `Failed to fetch dynamically imported module` means the dev server's dep optimizer went stale (a dep imported only from a lazy chunk or `import()` was discovered mid-session, or the lockfile changed under a running server). Triage first: `curl 127.0.0.1:5173/api/plugins/<name>/` (401 = backend fine) + `manage.py check`, then hard-reload / `npx vite --force`. A dep reachable only through lazy/dynamic imports must be listed in `optimizeDeps.include` in `frontend/vite.config.ts` (currently `dompurify`, `jspdf`, `html2canvas-pro`). See `03-FRONTEND-PATTERNS.md` §17.
- **Production admin routing** — `/admin/`, `/static/`, and the rate-limited `/admin/login/` are proxied to the backend in `frontend/docker/nginx.conf.template` (fixed 2026-09-27 — none of the three existed before, so admin silently fell through to the SPA and was completely unreachable in production despite docs claiming otherwise). The file is a `.template` now, not a static `.conf` — nginx's built-in envsubst-on-templates entrypoint renders it at container start so `${ONLYOFFICE_ORIGIN}` (CSP allowlist for the OnlyOffice document editor, empty/no-op if unset) can be substituted from a real env var. CSP is enforcing (flipped from report-only). Before editing this file: it still has plenty of native `$lowercase` nginx variables (`$host`, `$remote_addr`, `$trusted_ingress`, etc.) — envsubst only touches names that match an actual (conventionally-uppercase) container env var, so don't rename a new env var to something that collides with an nginx variable name.
- **Heavy feature libs need a dynamic import, not just a lazy-loaded page** — route-level `React.lazy` (done for every page since 2026-09-10) doesn't defer a *statically*-imported heavy dependency inside that page; it still ships in the page's own chunk graph and loads on page visit, not on use. Real case: `EngagementVisualizationPage.tsx`/`TLScorecardVisualizationPage.tsx` statically imported `captureChartsToPdf` from `pdfExport.ts` (html2canvas+jspdf, 663KB — the single largest chunk in the app), so visiting either page ate that cost even without clicking "Export PDF". Fixed 2026-09-27: `await import(".../pdfExport")` inside the click handler itself. Check bundle composition with `ANALYZE=true npm run build` (writes `dist/bundle-stats.html` via `rollup-plugin-visualizer`, gated off by default) before assuming a route-lazy page is fully deferred.
- **Payroll run access is scoped at the run level, not automatically at the line level** — `PayrollRunViewSet.get_queryset()`'s `_allowed_payroll_user_ids` scoping only decides which `PayrollRun`s a plain team leader can reach (any run containing ≥1 of their own team's lines); a run is company-wide, so reaching it must NOT imply seeing every line inside it. `lines()`/`payslip()` re-apply the scope via `PayrollRunViewSet._scoped_lines(run)`; `export_excel`/`export_pdf` (one consolidated file, can't be filtered per-line) and `period_closure_status` (lists every user in the run) instead require unrestricted access via `_ensure_unrestricted()`. The run row itself is company-wide too: `PayrollRunSerializer` gets `scoped_user_ids` from `get_serializer_context()` and returns `line_count`/`totals` computed from the viewer's own lines only (`aggregate_line_totals`) — any new run-level aggregate must be scoped the same way. Real IDOR fixed 2026-09-27 — a scoped TL could previously read/download any other team's salary data through a run they could only partially see. This "parent-object scope ≠ child-object scope" pattern is worth checking anywhere else a `get_queryset()` scope gate is followed by a custom `@action` that reaches into the object's related rows (`.all()`, not the scoped subset). See `.devin/plans/plan-security-perf-cache-audit-2026-09-27.md`.
- **Reference-table read caching** — `CacheKey.dashboard_reference(list_name, fingerprint)` (`apps/core/cache_constants.py`) + `build_query_fingerprint`/`get_cached_response_data`/`set_cached_response_data` (`core/utils/cache.py`) is the shared pattern for caching a shared (non-user-scoped) list endpoint; it reuses the `v{version}:dashboard:*` namespace so the pre-existing `CacheInvalidationMixin` (already wired into 9 viewsets before any of them actually populated that namespace — dead invalidation until 2026-09-27) invalidates it for free. Check the cache *before* any "ensure singleton exists" `get_or_create` query, not after — otherwise a cache hit still costs a DB query (real bug caught by `GlobalSettingsViewSet`'s own test). A `ReadOnlyModelViewSet` with no API write path (e.g. `DashboardWidgetViewSet`, admin-managed only) uses TTL-only caching, documented inline — don't invent invalidation wiring for a write path that doesn't exist. **Test-cache leakage risk**: Django's test runner never clears `cache` between `TestCase`s (only rolls back DB transactions) — any new test that GETs a cached list endpoint must call `cache.clear()` in `setUp()` itself (see `apps/dashboard/tests/test_reference_cache.py`); there is no global reset hook yet (Phase 6 candidate in `.devin/plans/plan-security-perf-cache-audit-2026-09-27.md`).
- **Optional-plugin imports must fail closed, never fail open** — the sanctioned pattern for a core/plugin file conditionally importing another plugin's service (control_room, audit_log, etc.) is `except ImportError:` only, never bare `except Exception:` swallowed into a permissive default. `except ImportError: pass`/`return True` means "plugin not installed, feature doesn't apply" — a real bug in the imported function must propagate, not silently grant access. Real case: `apps/reports/viewsets.py`'s `CanViewReports.has_permission` caught bare `Exception` around `control_room.services.scope_service.get_access_for_user` and returned `True` (fail-open) on any error; fixed 2026-09-27 to `except ImportError` only, matching the existing narrow pattern in `core/mixins/permissions.py:536,756`. See `.devin/plans/plan-security-perf-cache-audit-2026-09-27.md`.

- **`text-primary` is a different role from `bg-primary` (2026-10-03)** — `text-primary` resolves from `--primary-text` (dark `262 83% 68%`), while `bg-`/`border-`/`ring-primary` keep the `--primary` fill (`262 83% 58%`). One lightness cannot serve both: the fill needs L<=62% so white button labels clear AA, the text needs L>=68% to clear AA 4.5:1 on a dark card (measured live; the old shared value was 3.07:1 on a card, 3.45:1 on the page). The split is declared once in `tailwind.config.js`'s `textColor`, so no call site changed — do not "fix" a link by editing `--primary` (that restyles every button app-wide, 192 `bg-primary` uses), and do not hardcode a violet. Light mode is intentionally identical (`--primary-text == --primary`). Still open, on other tokens: the 10px notification count and the sidebar "Log Out" label both measure 4.38:1. Target size is WCAG 2.2 SC 2.5.8 AA (24x24): link-shaped actions need `inline-flex min-h-6 items-center`, not `inline-block text-xs`.

- **Site backup/restore** — hard-gated to `is_superuser` only (`SuperuserOnlyMixin` in `plugins/site_backup/viewsets.py`), stricter than the platform's usual staff-or-plugin-manage-grant pattern, because a restore can overwrite or delete any row. `dumpdata` deliberately omits `natural_foreign`/`natural_primary`: any model defining `natural_key()` (e.g. `auth.Group`, `auth.Permission`) has its PK stripped by those flags and re-resolved by natural key against whatever the DB looks like *at restore time*, which silently reassigns PKs and breaks the PK-based new/overwritten/db_only classification the restore preview depends on — do not re-add them. `contenttypes`/`sessions`/`site_backup` are excluded from every fixture. The FK dependent-closure graph (`services/dependency_graph.py`) is built from Django's own `_meta.related_objects`, not hand-rolled DB introspection. A model's "rows missing from the backup" are only ever deleted when explicitly opted into per-model via `delete_missing_models` — approving a model for create/update never implies deletion. `migration_state_hash` (sha256 of the applied-migrations set) blocks restoring a backup onto a schema it wasn't taken from. Read `.devin/context/PLUGINS/07-backup-restore.md` before touching this plugin.
- **TL engagement snapshots** — `TLApprovalMetric` is a real snapshot table (not computed live), populated by `services.compute_tl_metric` and read by every `TLEngagementMetricsViewSet` action. Staleness is auto-healed on read: `_ensure_fresh()` recomputes any row where `is_stale()` is true before serving/exporting it — there is no celery/cron scheduler in this repo, so this on-read check is the only thing keeping data current; do not remove it without adding a scheduled job instead. Aggregation math (`aggregate_rows` in `services.py`) is shared by `summary()` and `excel_export.py` so the two can never drift. Aggregates are weighted (approval = total approved/total decided; score/trend weighted by team_size/decided, never mean-of-means/rates); surfaced `computed_at` is `max`, never `min`. Pages always render subtitle (month + freshness), `ErrorCard` + retry on `isError`, tone tokens only, per-type aging breakdown, sidebar visible to TL + staff.
- **Plugin sidebar slots — two, not one** — `sidebar-nav` (main TL/employee sidebar, `Sidebar.tsx:130`) and `admin-sidebar-nav`/`admin-sidebar-nav-system` (admin panel, `AdminSidebar.tsx:165-166`) are separate `injection_slots` entries in `plugin.py`. A plugin only shows where it registers a slot for — compare `analytics`/`control_room` (register both) vs `engagement`/`tl_scorecard` (`sidebar-nav` only — TL features deliberately have no admin surface since 2026-10-01). Before calling a missing link "regression", check `get_frontend_metadata()`'s `injection_slots` list first — it may never have registered that slot.
- **Plugin metadata/permissions self-heal on refocus, deliberately breaking the app-wide query convention** — every other `useQuery` in this app sets `refetchOnWindowFocus: false` (the `QueryProvider` default, `lib/queryOptions.ts`, `useDashboardData.ts`) to avoid refetch storms on tab-switch. `PluginContext.tsx`'s active-metadata query and `usePluginPermissions.ts`'s permission query are the two deliberate exceptions (`refetchOnWindowFocus: true`, `staleTime: 0`) — they drive the entire sidebar/admin-panel injection surface and the dashboard widget picker, and restarting the backend (enabling a plugin, granting a permission) never touches the browser tab, so nothing else would ever refetch them; a stale value here looks exactly like a missing sidebar link/widget, not a backend bug. Do not add `staleTime` back to `usePluginPermissions` (`refetchOnWindowFocus` only refetches *stale* queries). `PermissionContext`/`useVisibleNavItems.ts` are NOT part of this class — they're synchronously derived from `useAuth()`'s `user` object, no network fetch, no staleness risk. If you add another context/hook that gates plugin-driven UI on a backend fetch, apply the same pair of options and note it here.
- **Client model & assignment** — canonical `Client` model is `apps/overtime/models/core.py` (`name`, `code` unique, `is_active`), reused by every plugin needing clients (never redefine). Assignment is `UserProfile.clients` M2M (`apps/users/models/core.py`), not a per-plugin through table. "Has ≥1 client assigned" is NOT an existing permission-manifest gate — `get_permission_manifest()` only supports role lists, so a client-count check must be done imperatively (viewset/queryset), same as `ticket_kpi`'s `_validate_client_ids` pattern (`plugins/ticket_kpi/viewsets.py`).
- **File uploads** — plain Django `FileField` on local disk (`upload_to='<dir>/%Y/%m/'`), no S3. Centralize size/extension checks like `plugins/ticket_kpi/upload_validation.py`'s per-purpose policy dicts + `validate_upload()`, called before any `file_obj.read()`. Frontend drag-drop uses native HTML5 `onDrop`/`dataTransfer.files` (`ImportFileDropzone.tsx`, ticket_kpi `FileInput.tsx`) — no `react-dropzone` installed. `@dnd-kit/core`+`sortable` are installed for reorderable lists, not files/trees — no folder-tree/file-explorer component exists yet.
- **Weighted aggregates & multi-query gating** — when normalizing a zero/falsy weight (`w or 1`), apply it identically to numerator AND denominator, never just one (caused a real score-inflation bug in `weighted_mean`, `plugins/engagement/services.py`). When a component's visibility depends on a threshold over data from one React Query source, put the check inside the component using its own render data — never gate from a second, independently-refetching query (caused a race in `TeamComparisonChart`).
- **HBPR (HR Business Partner, Italy)** — database role `hbpr`: a **read-only governance observer** of explicitly assigned Albanian TLs. Source of truth: `docs/hbpr-and-scorecard.md` — read it before touching anything HBPR. Non-negotiables: (1) Scope is a stored `HbprAlbanianTlAssignment` (one open row per AL TL, evidence-bearing rows never deleted — the PROTECT FK is honoured by filtering, never weakened; evidence-free ended rows older than 6 months are purged by `purge_ended_assignments` — no scheduler, so it runs lazily in the staff-only list and at boot via `purge_hbpr_archive`; every write goes through `apps/users/services/hbpr_assignments.py`) resolved by `hbpr_scope.py` — never a global population. `effective_to` is the LAST day in effect, not a switch: test openness only through `in_effect_q()`/`unfinished_q()` (`hbpr_assignments.py`), never `effective_to__isnull`. (2) Read-only: the HBPR slice applies to safe methods only; PIP approve/reject and promotion decide are staff/HR-only, evidence is authored by the assigned AL TL only (staff audit, never write), an HBPR exports only evidence of assignments it owns. (3) Employee one-on-ones are unreachable through ANY door: every HBPR-readable scorecard viewset must DECLARE its policy (`HbprScopedQuerysetMixin` raises `TypeError` otherwise), `test_hbpr_invariants.py` walks every route, the scorecard aggregate masks `one_on_one_compliance_pct`. (4) HBPR-only users are denied Calendar, Leave, Organigrama, Skills, Ticket KPI, Engagement, My Records, overtime, standby and reports (manifest `denied_roles`/`denial_override_roles` + `HbprBlockedMixin`; backend `is_hbpr_only` mirrors frontend `isHBPROnly`; multi-role users keep the other role's access). `docker/entrypoint.sh` must keep running `sync_plugins` → `seed_plugin_permissions` → `grant_hbpr_plugin_access` (pinned by `apps/plugins/test_hbpr_boot_path.py`). (5) `hbpr` is a managed role: every admin `roles` list must include it; revoking `hbpr`/`albanian_tl` with an open assignment is a structured 400; a new admin `@action` on `UserViewSet` must join the `IsAdminUser` list in `get_permissions`. (6) Notifications: five `hbpr_*` preference groups (`preference_group`), recipients only from the owner AL TL's open assignment, change detection via `TrackedFieldsMixin` (never a pre_save SELECT). (7) The `/hbpr` workspace pages records and evidence **server-side**: `hbpr/records/` delegates to the resource viewsets — never re-implement scope there; the `kind` vocabulary `pips|promotions|idle|absences|meetings|reviews` is shared with the notification deep links.
- **Search/export must not undo redaction (2026-10-04)** — a `?q=` filter runs in SQL *before* the serializer blanks a field, so searching a redacted column is an oracle (hit/miss reveals hidden text). `HbprScopedQuerysetMixin` therefore splits `search_fields` (visible to everyone in scope) from `private_search_fields` (matched only on rows `own_q` says the viewer owns; staff all) — put any column an `_OwnerOnlyNotesMixin`/`to_representation` blanks (`notes`) in the private list, never the public one. Every CSV/export writer must neutralise free text that starts with `= + - @ 	 
` (prefix `'`): `plugins/tl_scorecard/csv_export._cell` (server) and `records/recordsCsv.ts` (client) — reuse them, don't hand-roll another writer. Pinned by `test_search_cannot_probe_private_notes` and `CsvFormulaSafetyTests`.
- **TL scorecard** — every metric is computed live per month (no snapshot, unlike engagement's `TLApprovalMetric`); `export`/`scorecard` share `build_scorecard`/`governance_records` so evidence exports cannot drift. TL-facing plugins have no admin surface (`/admin/*` is `SuperuserRoute`-gated, so a TL-visible admin-sidebar link is dead). Nobody may decide or approve a record they are part of, staff included. Frontend never statically imports another plugin's module (hit its REST endpoint). `pages/TLScorecardPage.tsx` is orchestration only (sections under `components/scorecard/`); an HBPR-only viewer is redirected to `/hbpr` before any query fires and `viewer.canReview` is `isStaff`. The AL TL's partnership section reads `GET .../partnership/`. A dialog that seeds fields from an `initial` prop must be mounted only while open and keyed (`key={editing?.id ?? "create"}`). The Records tab's table is a preview: `RecordDetailDialog` is the full read view, and it renders only what the **list** serializer already returned (`attendees`, `status_updates` are embedded — opening a record must fire no request), labelling private vs shared text to match the API's redaction instead of re-deriving it. `POST .../idle-status-updates/` (one entry per flag per week) is the only TL-authored child record with a UI; meeting attendees stay read-only (no TL-scoped member picker exists). EPR stage completion is evidence-bearing: `POST .../epr-cycles/{id}/complete_stage/` is the **only** writer of `*_completed_at` (read-only on PATCH, same rule as `Absence.addressed_on`) — it stamps the stage and creates an `EPRStageRecord` (summary required, `reference_url`, `recorded_by`, `shared_with_employee`) atomically; a bare click is not evidence. My Records emits `stage_summaries` for shared rows only; the HBPR embed on `EPRCycleSerializer` exposes existence metadata (`has_reference`, `recorded_by_name`), never summary text or the URL — and the standalone `epr-stage-records/` endpoint is `hbpr_no_access` because it serves the full serializer (the embed is the HBPR's only read path). `GET .../hbpr-evidence/year-end-pack/?assignment=&year=` packages held-vs-expected cadence + both EPR participations for the TL's year-end review; it must use `_scoped_queryset` (not `get_queryset`) or the `?year=` `reporting_year` filter drops every `NULL`-year cadence row. Details: `docs/hbpr-and-scorecard.md`.

## Verification Commands

Targeted while iterating; the full pass exactly once, after implementation.

```bash
# Iterating — narrow the path, never the whole suite
py -3.14 manage.py check
py -3.14 manage.py test apps.<app>.tests.<name>
cd frontend && npx vitest run src/<path> && npx eslint src/<path>

# Full pass, once at the end
py -3.14 manage.py makemigrations --check && py -3.14 manage.py test
python -m ruff check --output-format=concise <changed .py files>
cd frontend && npx tsc --noEmit && npx vitest run && npm run build
```

Production is Python 3.12 + Django 6.1.1; the default `python` is 3.11 + Django 5.2 and hides Django-6 differences, so use `py -3.14` for Django commands.
